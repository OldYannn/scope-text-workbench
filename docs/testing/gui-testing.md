# GUI 测试、Computer Use 与人工验收规范

本规范用于明确自动化测试、Codex 的 Computer Use（计算机界面操作）和项目负责人人工验收之间的边界。目标是让每次测试的执行者、步骤和证据都清楚可追踪，避免 Codex 与项目负责人同时操作同一个 SCOPE 界面。

## 1. 自动化验证优先

凡是能够通过以下方式充分验证的行为，默认不得为了重复验证而调用 Computer Use：

- Python、Rust 或 React 单元测试；
- React 组件测试；
- NDJSON 协议契约测试；
- 跨进程集成测试；
- CLI 命令；
- Lint、Format、类型检查和构建检查；
- CI 中的跨平台构建与测试。

内部状态转换、算法结果、错误代码、进程消息路由、取消语义和可复现清单等行为，应优先在稳定的自动化 seam（可观察公共边界）上验证。

## 2. Computer Use 的适用范围

Computer Use 只用于命令和自动化测试无法充分验证的 GUI 特有行为，例如：

- 应用或安装程序能否真实启动；
- 按钮能否点击，键盘焦点和交互流程是否正常；
- 界面状态是否按预期变化；
- 安装、首次启动和卸载流程是否真实可用；
- 只能在 GUI 中复现的问题；
- 布局、遮挡、截断、响应式呈现和其他视觉异常。

Computer Use 不应重复证明已经由自动化测试充分覆盖的内部业务逻辑。GUI smoke test（冒烟测试）应短小、目标明确，以最少步骤验证关键用户路径。

## 3. 调用前必须定义 Test Flow

调用 Computer Use 前，Codex 必须先在聊天中写明 Test Flow，至少包括：

1. 要启动的应用、构建类型和版本；
2. 要验证的具体流程；
3. 每一步操作及预期结果；
4. 遇到非阻塞问题时是否继续；
5. 出现哪些情况时立即停止。

示例：

> Test Flow：启动本地 Debug `.app`；确认首页出现；点击“运行诊断”；确认进度和终态发生变化。视觉轻微偏差记录后继续；应用崩溃、出现权限请求或界面状态来源不明时停止并回到聊天说明。

Test Flow 没有定义完成前，不开始 Computer Use 操作，也不进行没有明确目标的长时间 GUI 探索。

## 4. Computer Use 执行期间的操作权

Computer Use 开始后，默认由 Codex 独立操作目标应用。项目负责人不需要主动点击、输入或改变 SCOPE 的界面状态。

如果确实需要人工介入，Codex 必须先回到聊天中提出单一、具体、可确认的请求，例如：

> 现在需要你点击“开始诊断”，完成后告诉我界面显示的结果。

在收到这种明确请求前，Codex 不得假定项目负责人会接管，也不得把等待人工操作当作测试步骤。

## 5. 停滞与异常处理

Computer Use 无法继续或疑似停滞时，不得默默等待人工接管。Codex 应停止继续点击并在聊天中说明：

- 当前停在哪一步；
- 已观察到的界面状态；
- 无法继续的原因；
- 是否需要项目负责人介入；
- 如果需要，只说明下一项具体人工操作。

如果自动化测试已经为该行为提供充分证据，可以结束 GUI 补充验证，并明确记录 Computer Use 未完成的范围。不得把未执行的 GUI 步骤写成“已通过”。

## 6. Project Owner UAT 与 GUI QA 分离

Project Owner UAT（项目负责人人工验收测试）是独立阶段，不与 Codex 的 Computer Use GUI QA 混在同一次测试中。

当一个 Milestone 已形成可供真实用户操作的功能时，可以在自动化测试和必要的 Computer Use QA 完成后，单独提供非技术用户可执行的 UAT 清单。每一项只包含：

- 操作步骤；
- 应看到的结果；
- 项目负责人需要反馈的内容。

UAT 未由项目负责人实际执行和反馈前，证据状态只能写为“待 UAT”，不能写为通过。

## 7. 测试证据等级

后续开发汇报必须标明证据类型，不使用没有来源的“审查通过”。

| 证据类型              | 含义                                                 |
| --------------------- | ---------------------------------------------------- |
| Automated Test        | 本地单元、组件、契约或集成测试产生的可重复结果       |
| CI Build              | GitHub Actions 等持续集成环境中的构建和测试结果      |
| Codex/Subagent Review | Codex 或子代理根据规格与项目规范进行的代码／文档审查 |
| Computer Use GUI Test | Codex 按预先声明的 Test Flow 执行的 GUI 测试         |
| Project Owner UAT     | 项目负责人按照独立清单执行并反馈的人工验收           |
| External Review       | 外部测试者、研究者或独立审查者提供的验证结果         |

汇报时应同时说明通过、失败、未执行或受阻，必要时附测试数量、平台、构建类型、提交 SHA 或 CI 链接。

## 8. Windows-first 的平台验证分层

SCOPE 正式采用 Windows-first，cross-platform supported（Windows 优先、跨平台正式支持）策略。Windows 是最终用户体验的参考平台，macOS 是当前主要开发环境并保持正式支持。两个平台要求核心研究能力和结果一致，不要求操作系统原生界面像素级一致。

Windows 验证必须区分以下三层：

| 层级                      | 主要内容                                                  | 能够证明                             | 不能替代                             |
| ------------------------- | --------------------------------------------------------- | ------------------------------------ | ------------------------------------ |
| Windows Automated Test    | Rust、Python、React、NDJSON 协议、sidecar 和可复现清单    | 内部逻辑和跨进程契约可重复验证       | 真实 GUI 交互                        |
| Windows GUI E2E           | CI 启动真实 Tauri Release 应用，运行一条最短 WebView 流程 | 应用可启动，关键页面和诊断交互可运行 | 安装器、安全提示、原生窗口和视觉体验 |
| Windows Project Owner UAT | 真实 Windows 环境中的安装、首次启动和人工观察             | 用户实际安装与使用体验               | 每次提交的自动化回归检查             |

Windows GUI E2E 只覆盖应用 WebView 内的关键流程。即使该检查通过，也不能写成“Windows 用户体验已经验证”。真实 Windows UAT 应至少检查 NSIS 安装、首次启动、SmartScreen / Defender、窗口、100% 与 150% DPI、中文字体和整体操作体验；它不是每次提交的阻塞条件，但应是重要 Milestone 和 Public Release 前的必要验收。

macOS 继续进行自动化测试和原生构建，并可按本规范使用最小必要的本机 Computer Use smoke test。不得为了平台表面一致而重复验证已经由自动化测试覆盖的内部逻辑。

## 9. 默认协作原则

> 自动化验证优先，Computer Use 最小必要使用；Codex GUI QA 与项目负责人 UAT 分开执行。

该原则适用于后续所有 Milestone。若某项测试因平台限制必须偏离本规范，应在执行前说明原因和替代证据。
